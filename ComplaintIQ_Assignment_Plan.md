# ComplaintIQ — Company Assignment Plan

Prepared September 30, 2026.

## Objective

Build a convincing, working financial complaint triage demo: enter a complaint, receive product and issue predictions, see a priority explanation and suggested department, and explore a dashboard populated with real model predictions.

The assignment should demonstrate three things: an actual fine-tuned small language model, measured performance against a simple baseline, and a polished application that makes the predictions useful.

Target: 10–14 focused working days, assuming familiarity with Python and basic web development. Allow extra time for free GPU availability. Budget goal: $0 using existing equipment and free notebook compute; no paid infrastructure is required for the local demo.

## Scope

### Required

- Single complaint analysis with editable text and several example complaints.
- Fine-tuned product and issue classification.
- Low/Medium/High priority calculated using a documented demo rubric, with the matched reason displayed.
- Suggested department from an explicit category-to-department mapping.
- Suggested next step from a short reviewed template library.
- Complaint history and analytics from saved predictions.
- Evaluation comparison and an explanation of training versus inference.

### Optional, only after the core works

- A short factual summary generated by the original instruction model in a separate pass. The classification adapter is not assumed to learn summarization. Check summaries for invented amounts, dates, and resolutions; omit this feature if unreliable or too slow.
- Batch CSV upload for small files, using a background worker and visible progress.

### Deferred

RAG, compliance prediction, company-specific adapters, authentication, multi-tenancy, automated customer replies, separate model servers, and large-scale deployment.

## Model and data

Use `Qwen/Qwen2.5-1.5B-Instruct` as the first candidate. Train a QLoRA adapter on a cloud NVIDIA GPU and export a quantized model suitable for Apple Silicon inference. This is a fine-tuning assignment, not pretraining from scratch.

Before substantial training, prove the export path: make a tiny adapter, merge it with the original checkpoint in the cloud environment, convert the merged checkpoint to a supported GGUF format, quantize it, and run it locally through a compatible llama.cpp runtime. Use the original floating-point model when merging, rather than assuming a four-bit training checkpoint can be merged safely. Pin compatible tool versions and retain the adapter separately.

Local target: four-bit 1.5B model, one request at a time, short context, short JSON output. An M1 with 8 GB shared RAM is a plausible target, but actual memory and speed must be measured on day one. Avoid leaving heavyweight development processes open during inference. If needed, benchmark a 0.5B candidate before committing to the final training run.

Data source: CFPB Consumer Complaint Database. Select English, non-empty narratives from a fixed recent date window. Use three product families, such as credit reporting, credit cards, and checking/savings accounts. Final selection depends on observed class counts.

Start with 6–10 well-supported issue classes across those families. Preserve original CFPB labels and document any mapping to shorter display labels. Include an unsupported-input/review state for unrelated complaints.

Initial dataset target: 6,000–10,000 total examples, subject to label availability. For 10,000 examples, aim for roughly 7,000 training, 1,500 validation, and 1,500 test examples. Deduplicate before splitting; keep near-duplicate groups together. Prefer later examples for the test set and record its natural class distribution. Do not force artificial balance in the test set.

Keep raw source data and cleaned records separate. Record source date, filters, label mapping, dataset counts, and random seed. Train on narrative text only; do not provide the answers or later company responses as input features.

Example classification target:

```json
{"product":"credit_card","issue":"billing_dispute"}
```

Use valid label IDs, validate output with a schema, and reject incompatible product/issue combinations. Permit a review status rather than silently substituting labels for invalid output. Do not display a model-written confidence percentage.

## Training and evaluation

1. Train TF-IDF + Logistic Regression locally as the baseline.
2. Evaluate the original instruction model with the same labels and prompt contract.
3. Run a 100–300 example fine-tuning smoke test, including export and local inference.
4. Run the main QLoRA experiment on the training set.
5. Compare all three approaches on the same held-out test set.

Initial training configuration to adapt after the smoke test: four-bit loading, LoRA rank 8 or 16, maximum sequence length 512 initially, micro-batch size 1–2, gradient accumulation, gradient checkpointing, and 1–2 epochs. Measure how much narrative text is truncated; increase length only if memory and runtime permit. Save resumable checkpoints outside ephemeral notebook storage and save the final adapter, tokenizer, configuration, and metrics.

Report product macro-F1, issue macro-F1, per-class recall, joint product/issue accuracy, invalid output rate, and a confusion matrix. Show local median and slow-request latency, hardware, and approximate memory use. Include 10–20 inspected successes and failures, plus a small unrelated-input challenge set.

No promised accuracy figure. If fine-tuning does not improve the baseline, report the result honestly and explain what the SLM offers or where it fails. Track the cloud model and exported quantized model separately; check for prediction changes on a fixed regression sample after export.

Priority is a demonstration policy, not a trained CFPB label. Example reasons: explicit ongoing unauthorized transactions, inability to access essential funds, or repeated unresolved disputes. Simple keywords can mishandle negation; inspect representative examples and make the reason visible. Department routing and action suggestions are also explicit rules/templates.

## Free GPU strategy

| Provider | Use | Limitation |
|---|---|---|
| Google Colab Free | Primary interactive training notebook | GPU type, access, and runtime are not guaranteed; sessions can end. |
| Kaggle Notebooks | Backup training environment | Weekly GPU quota; inspect the account's actual allowance and availability. Documentation describes 30 hours or sometimes more, depending on resources. |
| AWS Free Tier | Optional only | Listed free-tier EC2 instances are not GPU instances. Signup credits are not a guaranteed usable GPU allocation; verify service eligibility and GPU quota first. |

Do not make the assignment depend on AWS GPU access or temporary promotional credits. Colab and Kaggle are sufficient candidates for this model size, subject to availability. Port the same training logic between providers rather than maintaining two different pipelines.

Use free notebooks for training and notebook-based evaluation. Run the presentation application locally; do not rely on a Colab-hosted public web service.

## Application architecture

```text
Browser / Next.js
       |
    FastAPI
       |-- Local quantized SLM: product + issue
       |-- Rules: priority + reason + department + next step
       |-- SQLite: complaints + predictions + model version
       |-- Analytics queries
```

SQLite keeps this assignment easy to install and demonstrate. PostgreSQL can be added later without affecting the ML experiment.

Suggested endpoints: `POST /complaints`, `GET /complaints`, `GET /complaints/{id}`, and `GET /analytics`. Add CSV import only if time remains. Keep the model loaded once, serialize inference, cap input size, and provide useful loading and error states.

Store complaint text, predicted labels, priority and its reason, department, suggested action, processing status, model version, timestamps, and latency. Precompute predictions for 200–500 public complaints to populate the dashboard, clearly identifying them as the demo dataset.

## Presentation design

Three views:

1. Analyze: complaint input, example buttons, loading state, and clear result cards.
2. Complaint queue: searchable history, product and priority filters, and case details.
3. Dashboard: complaint count, priority distribution, common issues, product distribution, and a link to model evaluation.

Make the company demo a short story: paste an unfamiliar complaint, analyze it live, explain the priority reason and route, show it in the queue, then show measured model results. Include an ambiguous or unrelated complaint to demonstrate review handling.

Precomputed examples and baseline mode must be labeled. Keep a short recorded walkthrough as a presentation backup; do not pass cached output off as live inference.

## Deliverables and definition of done

- Source repository with one clear local startup procedure.
- Portable cloud training notebook and pinned dependencies.
- Dataset preparation script, labels, and split manifest.
- Fine-tuned adapter and instructions for obtaining the base model and local inference artifact.
- Evaluation report with genuine metrics and representative errors.
- Working local application with real inference and populated analytics.
- Five-slide presentation: problem, approach, model/data, measured results, live demo and limitations.
- Two-minute recorded walkthrough.

The core is complete when the company can watch a new complaint go through actual fine-tuned inference, see a coherent triage result, find it in the queue, and inspect a reproducible comparison against the baseline.
